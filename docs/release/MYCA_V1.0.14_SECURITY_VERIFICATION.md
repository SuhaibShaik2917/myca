# MyCA v1.0.14 Security Verification

**Target Release:** `v1.0.14`  
**Evaluation Standard:** Independent Security Audit Invariants & Trust Boundary Enforcement  

---

## 1. Tenant Isolation for Federated Identity Nonces

### Vulnerability Remediated
In `v1.0.13`, `public.idp_authentication_nonces` was provisioned without PostgreSQL Row Level Security (`RLS`), leaving it vulnerable to cross-tenant inspection and manipulation if application-level tenant context filtering was bypassed.

### Remediation Implementation
1. **Additive Migration `0028_idp_nonces_rls.py`:**
   - Executed `ALTER TABLE public.idp_authentication_nonces ENABLE ROW LEVEL SECURITY;`
   - Executed `ALTER TABLE public.idp_authentication_nonces FORCE ROW LEVEL SECURITY;`
   - Created policy `idp_auth_nonces_service_policy`:
     ```sql
     CREATE POLICY idp_auth_nonces_service_policy ON public.idp_authentication_nonces
         FOR ALL TO app_service_user
         USING (org_id = (NULLIF(current_setting('app.current_org', true), ''))::uuid)
         WITH CHECK (org_id = (NULLIF(current_setting('app.current_org', true), ''))::uuid);
     ```
   - Granted least-privilege `SELECT, INSERT, UPDATE, DELETE` to `app_service_user`.
2. **Dynamic RLS Discovery:**
   - `backend/scripts/audit_rls_security_comprehensive.py` dynamically queries PostgreSQL information schema for all tables containing `org_id` plus `organizations` and `global_users`.
   - Verified that `idp_authentication_nonces` is dynamically discovered and enforces `RLS=True` and `FORCE_RLS=True`.
3. **Cross-Tenant Attack Simulation:**
   - Attempted cross-tenant SELECT, UPDATE, DELETE, and INSERT spoofing against `idp_authentication_nonces` under `app_service_user`.
   - All cross-tenant operations were blocked with zero rows returned or SQLSTATE `42501` (`RLS_WITH_CHECK_VIOLATION`).

## 2. Browser Session Binding & PKCE S256 Cryptographic Verification

### Attack Vectors Defeated
- Authorization Code Injection
- Cross-Site Request Forgery (CSRF) in IdP Exchange
- Session Fixation / Replay from unauthorized browser clients

### Implementation Details
1. **Cryptographic Binding:**
   - During `POST /api/v1/auth/idp-nonce`, the server generates a cryptographically secure 256-bit entropy session token (`secrets.token_urlsafe(32)`).
   - The SHA-256 digest of this session token is persisted in `public.idp_authentication_nonces.session_binding_hash`.
   - The raw session token is transmitted to the client via JSON response body and `myca_auth_session` cookie (`HttpOnly; SameSite=Lax; Secure`).
2. **PKCE S256 Enforcement:**
   - The nonce request accepts an optional `code_challenge` generated by the initiating client (`BASE64URL(SHA256(code_verifier))`).
   - During `POST /api/v1/auth/idp-exchange`, the client must supply the original `code_verifier`.
   - The server recomputes the SHA-256 digest of `code_verifier` and performs a constant-time comparison (`hmac.compare_digest`) against `code_challenge`.
3. **Session Verification:**
   - The exchange request extracts the session token from the `myca_auth_session` cookie, `X-Session-Token` header, or JSON body.
   - Computes its SHA-256 digest and verifies it against `session_binding_hash`.
   - Failure to match or missing session token aborts with HTTP 401 `SESSION_BINDING_MISMATCH` or `MISSING_SESSION_TOKEN`.

## 3. Rate Limiting, Active Nonce Caps & Safe Pruning

### Abuse Protections
1. **Sliding-Window Rate Limiting:**
   - `NonceRateLimiter` enforces in-memory rate limits:
     - Per IP: 20 requests per 60-second sliding window.
     - Per Org: 30 requests per 60-second sliding window.
   - Excess requests are rejected with HTTP 429 `RATE_LIMIT_EXCEEDED`.
2. **Active Nonce Concurrency Cap:**
   - Maximum 5 active (`ACTIVE`, unexpired) nonces per organization.
   - Attempts to issue a 6th active nonce without consuming or waiting for expiration return HTTP 429 `ACTIVE_NONCE_LIMIT_EXCEEDED`.
3. **Safe Automatic Nonce Cleanup:**
   - Upon each nonce issuance, the service automatically deletes expired unconsumed nonces (`status = 'ACTIVE' AND expires_at < NOW()`).
   - Consumed nonces (`status = 'CONSUMED'`) are strictly untouched and permanently retained to maintain the cryptographic replay defense.

## 4. Exact Canonical Provider Trust Configuration

### Vulnerability Remediated
Previous releases used loose substring checks (e.g. `if "google" in issuer:`) which could allow attacker-registered domains such as `https://accounts.google.com.attacker.com` to be accepted as valid identity providers.

### Remediation Implementation
1. **Canonical Sets:**
   `backend/app/modules/auth/idp_verifier.py` defines exact immutable canonical issuer sets:
   ```python
   PROVIDER_CANONICAL_ISSUERS = {
       "google": {"https://accounts.google.com", "accounts.google.com"},
       "azuread": {"https://login.microsoftonline.com/common/v2.0", "https://sts.windows.net/common/"},
       "okta": set(),  # Configured via explicit MYCA_IDP_ISSUER
       "auth0": set(),  # Configured via explicit MYCA_IDP_ISSUER
   }
   ```
2. **Strict Cryptographic Algorithm Whitelist:**
   - `PROVIDER_ALLOWED_ALGORITHMS` restricts acceptable signing algorithms to asymmetric suites: `RS256`, `RS384`, `RS512`, `ES256`, `ES384`, `ES512`.
   - Symmetric algorithms (`HS256`) and algorithm `"none"` are rejected with HTTP 401 `ALGORITHM_NOT_PERMITTED`.

## 5. Multithreaded Concurrency Race Verification

### Invariant Tested
When multiple concurrent requests present the exact same IdP nonce, exactly one request must succeed and all other requests must be rejected as replays.

### Test Execution
- `test_multithreaded_concurrent_race_against_same_nonce`:
  - Spawned 5 concurrent worker threads via `concurrent.futures.ThreadPoolExecutor`.
  - All 5 threads raced simultaneously to consume the same issued nonce.
  - Result: Exactly 1 thread succeeded (HTTP 200). Exactly 4 threads failed with HTTP 401 `IDP_NONCE_REPLAY`.
  - Zero database deadlocks or race condition leaks observed.
